# 2026-09-08 — Daemon restart → mesh blackout (peer list empty, sessions "invisible")

**Status:** diagnosed on a live incident, fix pending. Owner: claudemesh repo session.
**Reporter:** flexicar-orchestrator session (evidence gathered read-only from `~/.claudemesh/daemon/daemon.log`, live CLI probes, and source on `main` @ 1.37.0).

## Symptom (user-visible)
After the local daemon restarted (launchd `com.claudemesh.daemon` KeepAlive), `claudemesh peer list` returned **0 peers on EVERY mesh** (flexicar, minery, legalrag, nedas-mesh…) for >40 min, although all 8 Claude sessions were alive. Sends by session pubkey reported `queued — no connected peer matches this key`. The whole orchestration went dark. User verdict: **"in case of daemon restart, sessions should be reconnected — this must not happen."**

## What IS working after the restart
- Registry rehydration (8/8), keypair re-derivation, attestation re-mint.
- Per-session broker WS: open + hello_acked for every session (so the broker's **in-memory** conn map has them, lease `online`).
- Inbound pushes: `claudemesh inbox` still lists prior messages; `/v1/events` SSE reconnects by itself (mcp/server.ts).

## What is BROKEN
1. **`list_peers` → empty on all meshes.** Broker `list_peers` handler = `listPeersInMesh(meshId)` = **DB** query `presence WHERE disconnectedAt IS NULL`. Empty ⇒ the DB presence rows are marked disconnected while the in-memory lease is `online` → **split-brain between in-memory conn map and the presence table**. Hypothesis (p≈0.8): the old daemon died without close frames → broker WS closes → lease grace (90 s) → new daemon reattached within grace (`session_hello reattach`, `restorePresence(pid)` fire-and-forget `void`) → later the **DB-level stale-presence sweeper** (keyed on `lastPingAt`) flips the rows back to `disconnectedAt = now` because pongs on the reattached WS don't refresh `lastPingAt` for the reattached presence id — or `restorePresence` lost a race with the sweeper. Either way `restorePresence` is a one-shot patch on a row the sweeper keeps re-flipping. Needs confirmation from broker logs (`ws hello reattach (lease)`, `session_hello reattach`, sweeper output) and `SELECT id,session_pubkey,disconnected_at,last_ping_at FROM presence WHERE …` on the broker DB (OVH via Coolify; SSH needs Tailscale re-auth right now).
2. **daemon.log = 1.0 GB** (disk at 95 %). `drain.ts:186` logs `drain_session_ws_not_ready` on EVERY drain tick for EVERY outbox row whose session WS isn't open — 117 797 lines in the last 20 MB, mostly for **stale session pubkeys from previous days** (4e00fc666559 ×70 676, cb26f393232e ×15 708 …) that will never reconnect. Rows are backed off but never expired; the log grows unbounded (launchd `StandardOutPath` → no rotation). This is the most plausible cause of the silent death of pid 85205 (I/O or disk pressure) — unproven.
3. **Session WS flapping** after rehydration (multiple open/close cycles per session, `broker_not_open` at drain time). Likely the same-pubkey ghost handling on the broker (`session_replaced` close of the older socket) racing the reconnect helper. Needs broker logs.
4. **Recovery UX**: nothing tells the user the mesh is in this state; `peer list` just says "no peers". A relaunch of a session does NOT fix it (proven twice today).

## Addendum 3 — ROOT CAUSE of "peer list empty on every mesh" (daemon side, confirmed in code + log)
`apps/cli/src/daemon/broker.ts` `connect()`:
```ts
this.lifecycle = await connectWsWithBackoff({ ..., onStatusChange: (s) => { this._status = s; ... } });
```
On 2026-09-08 19:28:17.889Z the first `hello_ack` timed out (5 s; broker busy with the storm) → `connectWsWithBackoff` **rejected** → `this.lifecycle` was **never assigned** (`broker connect failed for flexicar: Error: hello_ack_timeout`, ×9 meshes). But the helper's internal reconnect loop kept running on the same object: `broker_status reconnecting → connecting → open` at 19:28:20.187Z and `onStatusChange` set `_status = "open"`. Net state: **`_status === "open"` AND `lifecycle === undefined`** → every method gated on `this.lifecycle` short-circuits:
- `listPeers()`: `if (this._status !== "open" || !this.lifecycle) return [];` → `/v1/peers` answers `{"peers":[]}` in **30 ms** (measured; a real broker round trip is ≥200 ms) → `peer list` = 0 on all 9 meshes, forever, without any warning.
- `isOpen()` reads `this.lifecycle?.ws` → false → `send()` no-ops → outbox drain logs `drain_max_attempts err=broker_not_open` for member-keyed rows.
- `listSkills`, `getState`, etc. → same.
The control-plane presence (`daemon-94504`) IS online on the broker (DB row `XqS1ExHG`, disconnected_at NULL), so the WS is real — the daemon just lost its handle to it.

**Fix:** `connectWsWithBackoff` must hand back the lifecycle handle **synchronously** (before the first ack) and expose readiness separately (`await lifecycle.ready`), so a first-ack timeout cannot orphan a live reconnecting socket; `connect()` must not reject while the helper is still retrying; add an invariant check (`_status === "open" && !lifecycle` → log error + self-heal by re-running connect). Regression test: simulate hello_ack timeout on first attempt + ack on the second → `listPeers()` must return the broker's list.

**Two daemons in 6 s:** launchd respawned pid 93782 which died within 6 s (cause unknown — no `daemon_shutdown`, no crash report; the clean `shutdown()` handler only logs on SIGINT/SIGTERM) → doubled hellos/reattaches/dedups in the same 90 s grace window. Needs `daemon_exit`/`uncaughtException` logging and a launchd `ThrottleInterval`.

## Addendum 4 (CORRECTED 20:55Z) — after a daemon restart, delivery INTO Claude Code survives via the hook fallback; the live SSE push path does NOT
**Wrong claim retracted:** "no session receives pushes". Verified end-to-end after the clean restart: DM `req:ping-3` (20:41:11Z) → crm-api woke up with the injected prompt `[claudemesh] peer message arrived while idle - surface new inbox message(s)`, read its inbox and replied `ack:pong3` (20:41:39Z, in the orchestrator's inbox). So **messages reach sessions after a restart** — through the local hook layer (`~/.claude/hooks/claudemesh-wake-watcher.sh` for idle sessions, `claudemesh-inbox-drain.sh` on Stop/UserPromptSubmit, `claudemesh hook idle|working`), which polls the daemon via CLI/IPC on each tick and therefore survives daemon restarts. Latency = the watcher's poll interval, not immediate.

**What is dead after the restart:** the MCP plugin's SSE subscription (`/v1/events`) — the path that injects `<channel>` blocks **mid-turn** into a working session. Evidence: `lsof` shows none of the 10 live `claudemesh mcp` processes connected to the daemon (neither UDS `daemon.sock` nor TCP `127.0.0.1:47823`), and `mcp-*.log` has 0 `sse_event_received` after 20:40Z. Cause: `subscribeEvents` (`mcp/server.ts`) reconnects only on `res 'end'` / `req 'error'`; `res 'error'/'close'/'aborted'` (what a killed or `process.exit`-ed daemon produces) only logs to stderr — no reconnect, no heartbeat. Claude Code does not respawn the stdio server. Consequence: a **working** session no longer sees peer messages until its next Stop/prompt hook fires, and `now`-priority interrupts are lost until then.

**Fix (unchanged):** reconnect on every termination event + SSE heartbeat/idle-timeout + daemon `shutdown()` ends SSE responses before exit + replay unread on resubscribe + log reconnects to `mcp-<pid>.log`. Regression test: `kill -9` daemon under an active SSE client → resubscribed within 5 s of the new daemon accepting → a DM sent afterwards is `channel_emitted` (not only hook-drained).

## Addendum 5 (claudemesh repo session, 21:50Z) — verification of Addenda 1-4 + two more root causes + final design

**Verified against code + logs (broker `a9b735a` = HEAD, daemon 1.37.0):** Addendum 1's hypothesis (stale-presence sweeper flipping rows / pongs not refreshing `lastPingAt`) is **NOT** what happened — the `pong` handler bumps `lastPingAt` for the reattached presence id correctly. Addendum 2 (evict without closing the socket → ghost) and Addendum 3 (lost lifecycle handle) are **confirmed** and are the two visible mechanisms. Addendum 2's line "list_peers travels over the ghost session WS" is wrong (the session WS carries no RPCs) — Addendum 3 is the correct explanation for the empty list. Two more root causes found:

### RC-A (broker) — why a HEALTHY reattached lease was evicted: async gap in `ws.on("close")`
`index.ts` close handler: `if (conn.ws !== ws) return;` → **`await savePeerState(...)`** → `if (conn.leaseState === "online") enter grace else evict`. The `conn.ws === ws` check happens BEFORE the await, the lease mutation AFTER. Under DB latency the handler of the *dead daemon's* socket resumes after the *new daemon* has already reattached (`conn.ws` swapped, `leaseState = "online"`) and wrongly (a) starts grace on a lease whose new socket is alive, or (b) if a previous late handler already set `offline`, evicts immediately. Log proof: `ws close — lease grace started` for `ePekV8/sUNqkMO9/BsheM0ey` at 19:28:17.9–18.4, i.e. 0.85–1.2 s after `session_hello reattach` for the same pids, with **no `session_broker_ws_closed` in daemon.log** for those sockets; and 5 `ws evict full` at 19:28:16.4–16.9 with no `lease grace expired` (the "already offline" branch). Combined with Addendum 2 (no `ws.close()` on evict) the new socket becomes a zombie: OPEN on both ends, pings/pongs flow (the `ws` lib auto-pongs), no presence.

### RC-B (broker, degradation) — why the broker was slow enough for the race + the 5 s hello timeouts
`mesh.presence` has **2,491,950 rows** (2,488,046 with `disconnected_at` older than 30 d) and **no index except the PK**. `sweepStalePresences` (every 30 s), `listPeersInMesh`, `handleHookSetStatus` and the join in the fan-out paths **full-scan 2.5 M rows**; the postgres.js pool is the default 10. A restart storm (17 closes + 17 hellos + 9 timed-out re-hellos in ~10 s, each doing 4-8 queries) queued behind the scans → hello acks took 4–5 s (`hello_sent 13.25 → hello_acked 17.08–18.32`), which is what tripped the daemon's 5 s ack timeout and stretched the close handlers' awaits into the race window. Recurrence: guaranteed to worsen with N (≈ +1 row per session connect, never deleted). Fix = indexes + retention, not a bigger timeout.

### Final design (what ships in 1.37.1 / broker deploy)
**Broker**
1. Close handler: lease transition is **synchronous** (no await before it); `savePeerState` runs after, fire-and-forget; close code+reason logged. Eviction timer re-checks `leaseState === "offline"` before evicting (defensive).
2. `evictPresenceFully(pid, reason)`: if the socket is still OPEN → `ws.close(4004, "presence_evicted")` so the client reconnects and re-hellos. Reason logged.
3. Zombie sweeper (in the 30 s ping loop): any `wss.clients` socket that is OPEN, older than 60 s and not referenced by a `connections` entry → `close(4005, "no_presence")`.
4. Dedup scoped by role: member `hello` dedup only kicks `control-plane` presences; `session_hello` dedup only kicks `session` presences (fixes the mutual-kick chain of Addendum 2).
5. `sweepOrphanMessages` rewritten with the query builder (fixes the `Date`-param DrizzleQueryError; the hourly sweep has been failing).
6. Presence retention: hourly + at startup, batched `DELETE FROM mesh.presence WHERE disconnected_at < now() - 30 d` (20k/batch). Migration `0030_presence_indexes.sql`: partial indexes on `(member_id) WHERE disconnected_at IS NULL`, `(last_ping_at) WHERE disconnected_at IS NULL`, plus `(disconnected_at)` for the retention delete. Hello handlers log `latency_ms`.
**Daemon / CLI**
7. `ws-lifecycle.ts`: `createWsLifecycle()` returns the handle **synchronously**; `ready` resolves on the first ack; a hello-ack timeout only forces a backoff reconnect (never rejects/orphans). `close()` is always effective. Ack timeout default 5 s → 15 s. Both clients store the handle before awaiting `ready`. Invariant `status==="open" ⇒ lifecycle` holds by construction.
8. `drain.ts`: `drain_session_ws_not_ready` logged on attempt 1 and every 60th; not-ready path counts against the attempt cap; rows whose session pubkey has no registered session for >10 min → `dead session_gone`; any pending row older than 24 h → `dead expired`.
9. Rotating log sink (`daemon/log-sink.ts`): when `daemon up --foreground` runs without a TTY (launchd/systemd), stdout/stderr are redirected to `daemon.log` with a 20 MB cap × 5 files and a total-budget purge; the service unit's StandardOut/Err become `daemon.launchd.log` (pre-init crashes only). Existing oversized log is rotated on first start (incident excerpts preserved in `.artifacts/test-runs/`).
10. Forensics: `uncaughtException` / `unhandledRejection` / `exit` / `SIGHUP` / `SIGTERM` all write a `daemon_exit`/`daemon_uncaught` line synchronously before exit; plist gets `ThrottleInterval 10`.
11. MCP SSE (`mcp/server.ts subscribeEvents`): reconnect on `res close/aborted/error` and `req close`, idle watchdog (daemon sends `: keepalive` every 15 s → no bytes for 45 s ⇒ destroy + reconnect), reconnects logged to `mcp-<pid>.log`; daemon `shutdown()` ends open SSE responses before exit.
12. Operator signal: `GET /v1/diagnostics` (per-mesh member WS status + per-session WS status + log size); `claudemesh daemon status` prints it; `claudemesh doctor` adds: daemon version = CLI version, every member WS open, every registered session's WS open, **every registered session present in the broker's peer list** (the ghost detector), daemon.log size + stale service unit. Each with the one-command fix (`claudemesh daemon restart` / `claudemesh daemon install-service`). `peer list` prints a warning when the daemon's member WS for that mesh is not open instead of a silent empty list.
**Tests**: vitest for the lifecycle (first ack times out, second succeeds → same handle, `listPeers` returns the broker's list; `close()` before ack stops retries), drain expiry/rate-limit, log rotation, broker pure helpers (close-action decision, role-scoped dedup, zombie selection, orphan-sweep query shape).
**Release/deploy**: CLI 1.37.1 (npm + `cli-v1.37.1` tag) and broker via `git push gitea-vps main` → Coolify. Broker deploy first (the new close codes are harmless to old clients), then CLI upgrade + `claudemesh daemon restart` here, then the SIGKILL drill: `kill -9 <daemon pid>` → launchd respawn → `peer list --mesh flexicar` shows every live session within 10 s without relaunching any.

## Addendum 6 (claudemesh repo session, 22:15Z) — local reproduction results + RC-C (the actual eviction trigger) + two-daemon hazard

**Reproduction harness** (all local, nothing touched in prod): new broker (`bun src/index.ts`) on `:7955` against a throwaway pgvector Postgres (`docker cmh-test-pg`, migrations 0000–0030 applied by the runtime runner); isolated CLI 1.37.1 daemon (`CLAUDEMESH_CONFIG_DIR/DAEMON_DIR/SESSIONS_DIR=/tmp/cmh-drill/*`, `--foreground --no-tcp`, no TTY → rotating sink active); two fake sessions registered over IPC with live `sleep` pids and real session keypairs + parent attestations.

**Drill 1 — SIGKILL + respawn (the incident shape):** sessions visible in `peer list` at **t+1 s** after respawn; broker: `ws close 1006 → enter_grace` ×3, then `session_hello reattach was:offline` ×2; daemon: `sessions_rehydrated revived=2`. No eviction. PASS.

**Drill 2 exposed RC-C.** A minimal 20-line repro (two `session_hello` clients, same pubkey) against the local broker shows the old socket's `close` event logged BEFORE the `session_hello reattach` line, with `action: enter_grace`. Verified with an isolated script: **under Bun (the production runtime) the `ws` shim emits the server-side `close` event SYNCHRONOUSLY inside `ws.close()`; Node emits it on a later tick.** Consequence in the reattach path (`oldConn.ws.close(1000,"session_replaced")` → `oldConn.ws = ws`): the close handler runs while `conn.ws` is still the old socket → sees an online lease → starts grace + arms a 90 s eviction timer → the swap then sets the lease online again but the timer stays armed (the reattach's `clearTimeout` ran before the close) → **90 s later the healthy, reattached lease is evicted, socket left open → ghost.** In the pre-fix handler the same sequence ran with an extra `await savePeerState` in between, which is why prod logged `lease grace started` 0.85–1.2 s after `reattach` (DB latency) and `lease grace expired — evicting` ~90 s later for exactly the reattached pids (19:29:47–50). This is the primary trigger of the blackout; RC-A (async gap) is the second way the same handler could misfire. Fix: swap `conn.ws`/lease state BEFORE closing the replaced socket, clear timers AFTER; dedup paths `dropConnection()` before `close()`; the grace timer re-checks `leaseState` before evicting (this guard alone already prevented the eviction in drill 2 — logged `lease grace timer fired on online lease — skipped`). Pure-logic tests in `apps/broker/tests/lease.test.ts`.

**Drill 2 also exposed a two-daemon hazard (CLI):** `services/daemon/lifecycle.ts probeDaemon()` treated ANY probe failure (incl. a 2.5 s timeout against a busy-but-live daemon) as "stale" and `cleanupStaleFiles()` unlinked the live daemon's `daemon.sock` + `daemon.pid`. The daemon kept running unreachable; the next CLI call auto-spawned a second daemon; both rehydrated the same sessions and kicked each other's sockets with `session_replaced` every second (20 hellos/s on the broker), forever. Fixes: (a) a probe failure is "stale" only on `ECONNREFUSED`/`ENOENT` or a dead pid — otherwise "busy" (files intact, no spawn); (b) the daemon probes the socket for another live daemon before taking the lock, and re-asserts its pid file every 30 s (`daemon_pidfile_restored` / `daemon_pidfile_conflict`); (c) the WS lifecycle treats `1000 session_replaced` as terminal (whoever replaced us owns the identity; no reconnect fight), surfaced as `replaced: true` in `/v1/diagnostics`.

**Why the reattach was `was:"online"` after a CLEAN restart (new finding):** `shutdown()` awaited `b.close()` per client sequentially and then `process.exit(0)`; the WS close frames were still unflushed when the process died, so the broker saw no close, kept all 17 leases "online" until its 75 s stale-pong watchdog terminated them (20:41:59), and the new daemon's hellos 1 s after start reattached onto "online" leases → the RC-C path (close of the replaced socket) instead of the safe `was:"offline"` path.
